# Backup and restore verification (owner runbook)

Status: **blocked, not verified**. On 5 October 2026, the linked Supabase production project showed a Free organization plan. Its dashboard stated that Free projects have no managed backups, PITR is a Pro add-on, and restoring to a new project requires Pro or above with physical backups enabled. No independent dump was available in this workspace. The owner must provide a usable backup and an isolated restore destination before this drill can run. This repository still does not prove retention or recovery time. Never restore over production.

1. In the actual database provider console, record the provider, project, region, backup schedule, retention period, PITR availability and limits, and responsible operator. Save evidence in a private operations location, not Git. Confirm the plan includes these features; do not infer them from application code.
2. Record a maintenance timestamp and production migration status (`schema_migrations` names/count). Capture **aggregate only** counts of `users`, `expenses`, `income`, `goals`, `budgets`, `sl_spaces`, `sl_expenses`, `sl_bills`, `sl_shares`, `sl_payments`, `debts`, and `debt_payments`. Capture exact aggregate sums for `*_minor` columns and debt `numeric` columns; avoid logging row descriptions or user identities.
3. Trigger or select a provider-managed backup. Restore into a **new isolated disposable database** with separate credentials and no public API. Confirm the target name ends in `_test` or starts with `test_`, the host is not the production host, and production connection variables are absent from the test shell.
4. Time the restore from start to first successful connection. Check schema migration status on the restored database before applying any new migration. Compare table counts and exact financial sums against the backup point, accounting only for known writes made after that point.
5. Run `node scripts/reconcile-personal-money.js` on that disposable copy with `NODE_ENV=test`, `ALLOW_DESTRUCTIVE_TEST_DB=true`, and `TEST_DATABASE_URL` pointing to localhost. The script reports aggregate counts; investigate any non-finite, sub-minor, or out-of-range row privately. Do not apply migration 0016 to production until its preflight is clean on a current restore.
6. On the rehearsal restore, apply pending migrations, then run read-only reconciliation and scoped application smoke checks. Compare its financial totals and row counts with the pre-migration snapshot before any test writes. Run `npm run test:migrations`, `npm run test:db`, and API E2E only on a **separate disposable clone**: these suites create, update, delete, or rebuild test data and would invalidate the history comparison. Record failures rather than bypassing them.
7. Rehearse the recovery decision: who authorizes a restore, where the production app is paused, how new writes are prevented during cutover, how DNS/connection variables would be switched, and how to reverse the cutover. Do not execute a live cutover during the drill.
8. Store the drill date, backup identifier, recovery timestamp, measured restore duration, row-count and total comparisons, migration status, and approver in the private operations record. Delete the disposable copy according to the provider's retention policy.

Open questions requiring owner/provider confirmation: backup enablement, retention, PITR window, restore permissions, region, encryption settings, recovery-time objective, and recovery-point objective.
