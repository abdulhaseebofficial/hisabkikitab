# Personal money precision: staged migration plan (F5)

**Status (4 October 2026):** Local application reads, writes and money calculations now use the additive minor-unit shadows; migration 0018 adds the forward write path and keeps the legacy columns as checked mirrors. This is **not production verified**. The local disposable data reconciles, but there is no restored production copy, so historical production reconciliation is **Cannot confirm**. F5 is implemented and verified locally, pending that history check and staged rollout.

`scripts/reconcile-personal-money.js` reports aggregate per-column row count, non-finite count, sub-minor count, out-of-range count, and maximum minor-unit discrepancy. It requires the destructive-test guard and a localhost disposable database. Migration 0016 adds `BIGINT` shadow columns, fails if a value cannot be represented exactly to two decimal places, and maintains the shadows. Migration 0018 lets the application write the minor columns and mirrors their value to the legacy columns; legacy-only writes remain supported and are converted strictly. It rejects updates that supply inconsistent representations or cannot mirror cents in the legacy double column. It does not drop or backfill over any old column. The current supported-currency product policy is two decimal places for PKR, INR, BDT, AED, SAR, USD, GBP and EUR; adding currencies with different minor-unit precision requires a policy and schema review.

Preferred target: signed `BIGINT` minor units, consistent with Shared Living. The external API can continue returning decimal amounts for compatible values, but conversions must be centralized and reject fractions smaller than one minor unit, values outside a documented range, NaN and Infinity. PostgreSQL `NUMERIC` would simplify API compatibility but would still need string/decimal-safe JavaScript arithmetic; using minor units gives one integer rule across product modules.

Current floating monetary columns in `database/migrations/0001_initial_schema.sql` and later migrations: `users.monthly_income`, `expenses.amount`, `income.amount`, `goals.target_amount`, `goals.saved_amount`, `goal_contributions.amount`, `budgets."limit"`. Check all later migrations before changing the list. Debt `NUMERIC(14,2)` and Shared Living `BIGINT *_minor` stay unchanged.

Required staged release:

1. On a disposable restored copy, measure row counts, non-finite values if present, values beyond signed 64-bit minor units, and rows with more than two decimal places. Do not silently round those rows. Record currency and original double value per discrepant row in a private reconciliation artifact; do not put user financial values in logs or Git.
2. Add nullable `*_minor BIGINT` shadow columns by a numbered forward migration. Backfill only representable cent values using PostgreSQL `numeric` conversion and explicit checks. Reject the migration on unreconciled rows; do not drop or overwrite the original columns. Add checks and dual-write consistency constraints/triggers for the transition.
3. Switch repositories and calculations together: integer-safe input parser, integer sums in SQL, integer/BigInt arithmetic in services, decimal formatting at API edge. This local switch is implemented in migration 0018, `apps/api/src/shared/finance/personalMoney.js`, personal repositories/services, analytics/reports/advisor/notifications, `apps/api/src/shared/utils/calculations.js`, the guarded PostgreSQL parsers, and frontend money helpers/calculators. Preserve response keys and ordinary decimal shapes.
4. Verify every row against its original, account totals, category/month summaries, goal contribution ledgers and budget statuses on staging. Run migration tests, API E2E, concurrency tests and production build. Confirm currency precision policy for every supported currency before assuming two decimal places globally.
5. Keep migration 0018 additive and deploy the read/write switch only after a restored history copy passes reconciliation. The API returns numeric decimals through 999,999,999,999.99 major units; higher historical values are returned as fixed two-place decimal strings so cents stay exact. New inputs above that bound, non-finite inputs, and values with more than two decimal places are rejected. BIGINT and high-precision NUMERIC parser results stay strings; bounded safe database counts and ordinary debt NUMERIC values retain their existing Number API behavior. Monitor mirror/reconciliation results. Remove old float columns only in a **later** migration after an owner-approved backup and restore drill.

Local verification is recorded in `AUDIT_EVIDENCE_PHASE2.md`. It covers exact 0.10 + 0.20 sums, expense/income aggregates, budget remaining, goal contributions and progress, recurring clones, API JSON conversion, maximum accepted amount, large historical string responses, sub-cent rejection, and legacy/shadow consistency. A disposable local database reconciled with zero non-finite, sub-minor, out-of-range or discrepancy counts. A restored production-history reconciliation was not performed: **Cannot confirm**.

## Current path inventory and remaining float boundaries

The switched personal-money paths are expense and income create/update/list/summary; budget create/update/list and month summaries; goal target/saved values and contributions; planned monthly income; analytics/dashboard totals, categories, trend and budget status; report aggregates, CSV/PDF export values; and recurring-expense materialization. Database aggregates sum `*_minor` as BIGINT. API row shaping converts shadow cents at the response boundary and adds the minor field as a decimal string; goal contribution lists use the same shaping. Advisor budget/savings calculations and goal reminders derive from minor values. Frontend dashboard grouping and totals, upcoming recurring bills, expense amount bumping/validation, goal contribution previews, and public budget, split, goal, emergency-fund, debt-repayment, net-worth and freelancer calculators use integer cents for arithmetic.

The following float/decimal uses remain intentionally at boundaries: retained legacy `double precision` columns are checked mirrors maintained for staged compatibility; JSON continues to expose ordinary bounded major-unit numbers for API compatibility, while values outside the supported safe response bound are decimal strings; browser forms accept decimal text and submit JSON decimal values; formatting, chart dimensions and percentage display use bounded numbers but do not write calculated money back. Debt money uses its existing `NUMERIC(14,2)` contract and Shared Living money remains BIGINT minor units; neither is part of F5's personal-money column migration. No personal-money aggregate or balance calculation is intended to use legacy float columns. A future source audit should revisit these boundaries before any legacy-column removal.

This audit cannot confirm real historical value distribution or backup/restore capability. Therefore a production money migration in this phase would violate the no-silent-loss requirement.
