### Independently confirmed security/release defects

**Access-token revocation (A):** `signAccessToken()` signs `{sub,type}` with default `JWT_ACCESS_EXPIRES=15m`, while `signRefreshToken()` also carries `v=token_version`. `auth.middleware.protect()` verifies the access JWT and reloads the user but never compares a version or active session. `users.repository.setPassword()` and `revokeAllSessions()` bump `token_version` and clear stored refresh sessions. A guarded throwaway account was inserted, an access token signed, its version incremented, then `GET /api/auth/me` with that old token returned **200**. The account was deleted afterward. This proves an old bearer token survives password change/reset or refresh-replay revocation until expiry. Existing green security tests do not assert immediate access-token invalidation. A targeted version check and test are required before launch; no code was changed during this audit.

**CI origin (A):** `.github/workflows/ci.yml` static job executes `npm run build` with no origin variable. `apps/web/scripts/prerender.mjs` throws at line 10 when both origins are absent. The missing-origin invocation failed exactly as expected; the build passed with a deliberate inert HTTPS origin. No origin file is tracked. CI needs a canonical non-secret build origin and a real hosted rerun. The same CI composite omits `tests/e2e/personal-money.test.js` and does not run `test:security`; the explicit local results above cover this snapshot, but these should be considered for the later CI gate review.

**Scheduler release gap (C, with manifest/config step):** `GET /api/internal/recurring` rejects missing/short/wrong `CRON_SECRET` before DB bootstrap and propagates sweep failures. `tests/db/scheduler.test.js` passed. `vercel.json` contains rewrites but no cron entry, and `server.js` registers in-process timers only when directly run outside test mode. A Vercel-imported serverless app therefore has no proven punctual recurring trigger. Set the production secret, choose a reviewed schedule within provider limits, add the manifest entry or an equivalent external scheduler, and verify actual invocations/failure alerts before launch.

## F10 recurring Shared Living bill-copy continuation — 5 October 2026

The starting `sl_bills` schema had `space_id`, `period_id`, `request_id`, `request_hash`, `recurring` and visible bill fields, but no source or lineage ID. `copyRecurringBills` used a same-name/category existence query in the target period, so it could suppress a legitimate second bill. Its existing space row lock serialized authorized API calls, while `sl_bills_request_idx` protected only a caller's request ID. A copy's fresh request ID correctly distinguished a new month for F11, but provided no occurrence uniqueness across different requests.

Migration `0021_shared_bill_occurrence.sql` adds `recurring_origin_id` and `recurrence_identity_known` to `sl_bills`. Existing rows retain NULL in both columns; new rows default to known identity. The partial unique index `sl_bills_one_recurring_origin_per_period` enforces one generated row per `(space_id,period_id,recurring_origin_id)` even when a bill is soft deleted. No old bill, share, payment, period, amount, creator or activity row was merged, deleted or reassigned. Reapplication is safe in this repository's migration framework; an exact non-NULL lineage conflict raises `23505` before index creation. On a production-history restore, run the exact conflict query and inspect diagnostic groups of old recurring rows with the same `(space_id,period_id,name,category_id)` before rollout. Names/categories are candidate signals, not proof of common origin. Pre-cutover target periods containing any old bill and old source periods with same-name/category recurring candidates now return `409 shared.legacyBillReview`; an old populated month may need explicit review before a legitimate copy. No automatic history override was added. A restored production-history copy was not available: **production-history preflight and migration runtime Cannot confirm**. GROUP BY space_id, period_id, recurring_origin_id HAVING count(*) > 1;

## User-local financial date boundary continuation — 5 October 2026

The preceding F13 paragraph is a **dated snapshot**: its browser failure is resolved by this continuation, while its dependency counts and F13 status have not changed. `expenses.date`, `income.date` and debt transaction/due fields are `timestamptz` in the current schema, but their form fields are date-only. A `YYYY-MM-DD` request is converted by the current validators to UTC midnight; PostgreSQL retains that instant, and JSON serializes the date as ISO. The chosen financial day is therefore represented by the UTC date of that midnight value. Other `timestamptz` values, including `created_at`, `next_run_at` and actual payment timestamps, remain instants. Shared Living bill/expense date fields use SQL `date` and are separate. No historical row, migration or production data was modified.

Root-cause reproduction: `presetRange()` previously converted local `Date` objects with `toISOString().slice(0,10)`. At 2026-10-04 20:30 UTC, a Karachi browser's form day is **2026-10-05**, while its previous “This month” filter ended **2026-10-04**. Los Angeles at 2026-10-05 06:30 UTC has local **2026-10-04** while the prior filter ended **2026-10-05**.
